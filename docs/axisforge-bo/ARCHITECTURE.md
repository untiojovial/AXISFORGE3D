# AxisForgeBO: preliminary architecture and AxisForge3D boundary

Decision log. The opening sections preserve the initial repository inspection and proposed contracts. The implemented Python package, Node/WASM adapter and verified scope are described under **Implemented boundaries** below. See FINAL_AUDIT.md for current acceptance status.

## Verified repository facts

* The repository is a Rust workspace (edition 2021, minimum Rust 1.85) with domain, geometry, kinematics, collision, grasping, project-io, service, CLI and WASM crates (`Cargo.toml`). The core uses `nalgebra`, `serde` and `serde_json`; the latter enables `float_roundtrip`. The existing viewer is a separate browser front end. No Python API or network service is declared in this workspace.
* `crates/service/src/lib.rs:78` defines serde-tagged `Request`: `load_project`, `describe`, `set_joints`, `snapshot`, `solve_ik`, `plan_pick` and other operations. `Session` owns project, model, joint values and a registry (`:636`); it is stateful. `handle_json` (`:709`) consumes a JSON string in-process and emits `{"ok":true,"kind":...,"data":...}` or `{"ok":false,"error":"..."}`. This method is not itself a process transport or server. The CLI (`apps/cli/src/main.rs:87`) has individual commands, not a generic JSON request loop.
* `snapshot` accepts explicit joint `values` and returns `Snapshot` including collision, conditioning, joint-limit results and pose (`crates/service/src/lib.rs:325`). `set_joints` updates state. `plan_pick` takes body ID and `PlannerOptions`, operates from current session values, and returns `PlanReport`; it synthesizes and evaluates grasps internally, rather than exposing a general arbitrary candidate evaluator. The Rust API has lower-level primitives, but no proof was found that they already provide the full requested arbitrary grasp-evaluation contract.
* `PlanReport` includes plans, rejections, candidate counts, cancellation and timeout (`crates/grasping/src/planner.rs:264`); each plan includes quality and clearance (`:238`), while rejection reasons distinguish collision, unreachable and inconclusive (`:192`). A no-plan, timeout, cancellation, error, and physically infeasible evaluation must not silently become the same numerical observation. Planner timeout requires a native clock; WASM refuses it (`crates/grasping/src/planner.rs:59`, `:179`). Synthesis has a seed (`crates/grasping/src/candidate.rs:29`), but `PlannerOptions` does not expose it; do not claim end-to-end caller-controlled seed reproducibility without further work and tests. Planner's `seed` argument is a joint configuration, not an RNG seed (`crates/grasping/src/planner.rs:810`).
* The extension registry provides Rust `CandidateGenerator` and `QualityMeasure` traits (`crates/grasping/src/registry.rs:25`, `crates/grasping/src/quality.rs:123`). This is an in-process Rust extension point, not a proven dynamic plugin ABI or Python interface. `IMPLEMENTATION_STATUS.md` identifies native-only registry scope and simulation limitations; measurements are engineering approximations and do not validate physical grasping.

## Architectural boundary

Keep the scientific optimizer independent: a search space validates candidate values; ask produces an identified candidate, tell records a completed observation, predict exposes posterior quantities, and best uses an explicit minimization/maximization direction. Objective execution is outside this core. These are proposed contracts, not claims about code currently available. Backend, model and acquisition implementations should be replaceable through narrow interfaces, with explicit shape, dtype, noise and RNG semantics and no simulator dependency. Avoid creating empty modules for unimplemented algorithms.

An evaluator contract should carry a schema/version, experiment and evaluation IDs, validated candidate and optional context, objective direction and units, evaluator configuration, object identifier when relevant, and separately identified random seeds. Results should distinguish success, infeasible, timeout, cancelled and execution error; contain named objective/constraint values and units, diagnostic metrics, elapsed cost, provenance and optional reproducibility metadata. Validate all numeric values for finiteness; do not automatically train a surrogate on failures or fill missing objectives with invented penalties. The mapping from an unsuccessful outcome to an optimization observation must be an explicit experiment policy. Do not infer success probability or equivalence among epsilon, collision and grasp quality from planner reports.

The future adapter maps an agreed candidate schema to concrete AxisForge requests and maps responses without changing core optimization semantics. Start with a mock evaluator and mathematical benchmark evaluator. A snapshot-based adapter for joint configuration and a planner-parameter adapter are plausible future integrations, but arbitrary grasp evaluation requires an independently designed and tested AxisForge extension first. The exact metrics and constraints need a domain-specific mapping. Capture a versioned project snapshot/hash, build/version, full options, current joint state, all available seeds, thread/device settings, and error/timeout outcome; a seed alone is not a determinism guarantee. Isolate each evaluation in a fresh session or explicitly restore state; serialize access to a shared mutable session. An external timeout may terminate a process, while in-process cancellation requires a tested cancellation path: `handle_json` currently creates its own token.

## Communication alternatives

| Approach | Fit and evidence | Cost / decision |
| --- | --- | --- |
| Rust native API | Direct `Session::handle` and library traits already exist. | Lowest boundary overhead for Rust hosts; Python requires another bridge and Rust types/versions remain coupled. Candidate for a later Rust host. |
| Python binding (PyO3, possibly via a JSON facade) | Python scientific ecosystem could call a purpose-built Rust wrapper. | Additional native build and deployment/ABI lifecycle; verify thread safety, ownership, cancellation and packaging. pybind11 targets C++, so it is not a direct Rust binding choice. |
| C ABI / FFI | Possible via a new Rust `extern "C"` wrapper. | Stable serialized ABI possible, but ownership, buffer lengths, errors, panic containment and versioning need design and tests; no existing C ABI verified. |
| Local subprocess + framed JSON | Existing in-process JSON request/response shapes provide a natural wire representation. | Requires a **new** worker executable/protocol; the current CLI is not such a worker. Explicit framing, session lifecycle, output limits, cancellation, crash recovery and version negotiation needed. Promising isolation, not implemented or benchmarked. |
| REST / gRPC | Could support remote simulators and distributed workers. | Introduces service deployment, protocol/authentication and operational complexity. Neither is verified in the repo; defer until remote execution is needed and measured. |
| WASM | Workspace has a WASM front end. | Existing WASM clock limitation prevents planner timeout; no evidence it solves native scientific integration. |

No transport is selected as final until a representative end-to-end prototype has measured latency, memory, cancellation, reproducibility and packaging. A process boundary is a reasonable hypothesis for failure isolation, not an established compatibility claim.

## Persistence and plugins

Persist configuration, ordered observations and candidate IDs, model/backend versions and state, RNG states and pending evaluations using a versioned checkpoint schema; reject incompatible or corrupt files explicitly. Write atomically and test interrupted writes and reload equivalence. Never deserialize untrusted executable object formats. A future plugin mechanism should provide versioned, validated interfaces with explicit registration and documented dependencies; the existing Rust grasp registry does not establish a language-independent plugin system. Initial BO code can use ordinary dependency injection without a dynamic plugin loader.

## Test and approval gates

1. **Contract tests**: deterministic mock success, constraint violation, failed evaluation, timeout, cancellation, non-finite and malformed payloads, duplicate IDs, unexpected shape and unknown schema version. Verify failed evaluations cannot become silent numeric observations.
2. **State and checkpoint**: repeated ask/tell, objective direction, save/reload with pending requests and RNG continuation, corrupted/truncated checkpoint, atomic replacement and version mismatch. Explicitly specify concurrency behavior before testing races.
3. **Simulator boundary**: independently check `snapshot` against direct Rust service calls on a fixed project and joint vector; verify identifiers, units and collision response, resets, malformed inputs, timeout/cancellation and error propagation. A mock proves only the adapter contract, never compatibility with AxisForge3D.
4. **Real integration**: execute the eventual concrete adapter against a pinned native AxisForge build with fixed project content, parameters and available seeds; compare repeated results and source reports, including no-plan and partial timeout cases. Keep any robotic experiment outside the current scope. Measure overhead and memory against an agreed baseline. Native/WASM differences must be separately reported.
5. **Scientific gates**: mathematical reference checks, numerical degeneracies and benchmarks, coverage and independent review are required in addition to software tests. No gate is approved from this document alone. Any unsupported arbitrary-candidate mapping, reproducibility gap, unexecuted real integration, or unresolved high-severity audit issue blocks a compatibility claim and final approval.

## Implemented experimental boundary (pending independent approval)

The current Python optimizer supports `ask()` and `ask_batch(n)` with multiple reserved candidates and out-of-order `tell`/`fail`; methods and checkpoint snapshots use an in-process reentrant lock. Pool optimization is heuristic. For each pending point with successful observations in exactly the same context, the GP is temporarily fitted with a constant lie equal to the worst completed objective in canonical minimization units; pending points in a context without a completed observation are excluded from the fit. This is not an exact joint batch posterior. Different completion orders can change later decisions. A failed batch reservation rolls back RNG and reservations. Budget includes pending and all completed statuses. Checkpoints store reservations and RNG, and require the same registered acquisition name to be installed when loading.

Continuous decisions are mapped to the unit box. Mixed-space sampling uses normalized real and integer coordinates and one-hot categories; these choices imply a metric and do not establish its suitability for all categorical problems. Sobol and Latin hypercube sampling currently apply only to continuous boxes. A finite mixed space can exhaust the sampled pool even if another untried point exists. Contexts are compared using exact floating equality and their scale and decision-time provenance are caller responsibilities. The constant-liar implementation is experimental and lacks scientific batch benchmarks.

`integrations.axisforge3d.WasmService` runs one JSON request in a fresh Node/WASM process, enforcing an external timeout and reporting elapsed time and a SHA-256 digest of the supplied WASM artifact. `SnapshotEvaluator` maps a full joint vector to the service's Jacobian manipulability, reporting errors separately; this metric is dimensionful and is neither grasp quality nor a safety measure. The adapter uses the fixed demo session and is a narrow proof of connectivity, not a general simulator adapter. It does not yet support supplied projects, random seeds, grasp candidates, collision constraints, or external robot experiments. Real service tests require Node and a separately built existing `axisforge_wasm.wasm`; they skip when these are absent.

## Implemented boundaries

The installation target is the independent axisforge_bo Python package. Its NumPy/SciPy GP is deterministic given data and configured parameters. fit/predict protocols also accept external surrogates; optional PyTorch/BoTorch experiments have their own device and uncertainty contracts. BayesianOptimizer owns the reservation ledger and callbacks, with an in-process reentrant lock and atomically replaced JSON checkpoints. Cross-process concurrent writers to the same checkpoint are outside this contract. Exact model refits cost O(n³); small incremental additions reuse the experiment ledger, not a rank-one factorization. A finite pool restricts where a proposal can be selected. Mixed categories use one-hot features and integers use an ordered grid.

The implemented adapter invokes the existing WASM JSON ABI through a fresh Node process, checks response tags and computes SHA-256 from the bytes instantiated by the worker. The snapshot evaluator extracts one manipulability metric from the existing demo session. Its scope is restricted to the source-supported joint-vector evaluation, unit checking, elapsed cost, error and timeout paths. See test_axisforge_service.py for the real binary check. New scenes, hand models and grasp experiments were not part of this phase.

`TaskArchive` stores schema-versioned completed task records as finite JSON, with raw context, embedding, observation dictionaries, versions, seeds and model hyperparameters. Retrieval requires an explicit group allowlist and excludes held-out groups and tasks completed at or after the decision time; observation timestamps, when supplied, cannot exceed task completion. Euclidean embedding distance and a user-selected support threshold determine eligibility, followed by softmax of negative distance for normalized weights. Empty or out-of-support results explicitly return no task. Optional paired historical transfer and baseline validation losses reject transfer when mean transfer loss is worse. This simple rule is not a statistical test, a safety guarantee or evidence of improvement; the caller must choose leakage-free validation pairs, maintain group and timestamp correctness, and decide how to import selected observations. It complements contextual memory and does not automatically modify the optimizer.
